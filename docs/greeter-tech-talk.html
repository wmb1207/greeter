greeter

A custom Crystal-powered TTY login greeter for launching exactly the sessions this machine needs.

Why This Exists

  • Boot straight into a clean TTY UI.
  • Authenticate real system users through PAM.
  • Launch X11, Wayland, SSH, Moonlight, reboot, and shutdown flows.
  • Keep the whole login path small enough to audit.

The User Flow

Draw login screen
Read username and hidden password
Authenticate with PAM
Build session menu
Fork, drop privileges, exec

After the selected session exits, the greeter returns to the login prompt.

Tech Stack

Core

Crystal native binary, static types, Ruby-like syntax, small source tree.

System

Linux-PAM, LibC FFI, fork/waitpid, setuid/setgid, terminal ioctl.

Ops

Nix flake, NixOS module, systemd service, journald JSONL logs.

Core Design Choice

root greeter Owns the TTY UI and can authenticate the next login.
=>
user session child Drops groups, GID, UID, then execs the selected session.

Authentication

  • Uses custom Crystal FFI bindings to Linux-PAM.
  • Starts the login PAM service.
  • Supplies the password through a PAM conversation callback.
  • Runs pam_authenticate and pam_acct_mgmt.
  • Returns a live PAM handle for session setup.

The password is used for the callback and is not written to logs.

X11 Launch Model

greeter tty1
  |
  +-- supervisor child, still root
        |
        +-- pam_open_session
        +-- worker child
              |
              +-- chown tty
              +-- drop privileges
              +-- exec startx <wm> -- :display vtN
        |
        +-- wait
        +-- pam_close_session

Current pool: tty3 through tty7.

Why X11 Gets a Supervisor

  • The long-lived greeter parent should not own the user's graphical PAM session.
  • The supervisor owns pam_open_session, the worker, and pam_close_session.
  • The parent records the supervisor PID and immediately returns to the prompt.
  • That allows multiple X11 sessions to stay active at once.

Wayland Launch Model

greeter
  |
  +-- pam_open_session
  +-- fork child
        |
        +-- chown tty
        +-- ensure runtime dir when needed
        +-- drop privileges
        +-- exec compositor/session
  |
  +-- wait
  +-- pam_close_session

This path blocks the greeter until the compositor exits.

Static Actions

Power

Streaming

Runtime Environment

  • Sessions launch with clear_env: true.
  • Identity is rebuilt: HOME, USER, LOGNAME, SHELL.
  • Paths include user profile, Nix profile, system profile, wrappers.
  • Logind gets XDG_SESSION_TYPE, XDG_SEAT, and XDG_VTNR.
  • User services get XDG_RUNTIME_DIR, D-Bus, and Pulse/PipeWire endpoints.

TTY User Interface

  • Raw ANSI screen drawing.
  • Responsive terminal-width layout.
  • Noncanonical input for password masking.
  • Ctrl+L toggles us and dvorak console keymaps.

  • Logger JSONL shape and severity helpers.
  • Logger failure isolation.
  • Keyboard layout config parsing.
  • Fallback behavior for invalid keyboard layouts.
  • NixOS VM for manual PAM/session testing.

Limitations

  • Linux is the practical target; session integration is Linux-centric.
  • NixOS assumptions are baked into paths, wrappers, and service setup.
  • The binary must run as root or setuid-root.
  • PAM bindings are hand-written FFI, so ABI correctness matters.
  • .desktop parsing is intentionally minimal.
  • Wayland, SSH, and Moonlight sessions block the greeter.
  • X11 concurrency is capped at five sessions.

More Limitations

  • Static config is loaded only at startup.
  • No graphical accessibility features.
  • No localization.
  • No username chooser or avatar model.
  • No account/session policy UI beyond PAM and configured menu actions.
  • No automated integration tests for real PAM, logind, TTY ownership, Xorg, or Wayland.

Security Boundaries

Strong Parts

  • No shell for X session execution.
  • Explicit privilege drop before user exec.
  • Environment is cleared and rebuilt.
  • PAM account management is checked.
  • Logs avoid passwords.

Risk Areas

  • Root/setuid attack surface.
  • Direct TTY ownership changes.
  • Manual C ABI bindings.
  • Session commands from .desktop files and local config.
